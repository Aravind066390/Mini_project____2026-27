This is a small C++ wrapper around Linux TCP sockets. Its purpose is to hide the low-level socket API (socket(), connect(), bind(), listen(), accept(), send(), recv()) behind a simple Socket class.

The important idea is:

Your program
    ↓
Socket class
    ↓
Linux socket API
    ↓
TCP/IP
    ↓
Network

So instead of writing 30–50 lines of socket code every time, you can do:

Socket client;
client.connect_to("127.0.0.1", 8080);
client.put_file("ABC.mp4");

and on the server:

Socket server;
server.listen_on(8080);

Socket client = server.accept_client();

client.get_file("received.mp4");

Let's go through exactly how your library works.

6. recv_all()

This is basically the reverse.

bool recv_all(void *data, size_t size)

It guarantees that your function doesn't return until the requested number of bytes has been received, or an error occurs.

For example:

may internally do:

recv → 3000
recv → 4000
recv → 3000

Total:

10000 bytes

Then it returns true.

This is extremely important with TCP.

7. TCP does NOT preserve message boundaries

This is an important concept for understanding your library.

If the sender does:

send(fd, "HELLO", 5, 0);
send(fd, "WORLD", 5, 0);

TCP does not necessarily deliver:

HELLO
WORLD

It could arrive as:

HELLOWORLD

or:

HEL
LOWOR
LD

or another segmentation.

TCP gives you a byte stream.

Your send_all() and recv_all() functions solve part of this problem by explicitly specifying how many bytes need to be transferred.

32. Why the file doesn't get corrupted by TCP packet boundaries

This is another important concept.

Suppose your 8192-byte chunk is internally split by TCP:

send_all()
   |
   +---- TCP packet 1: 1460
   +---- TCP packet 2: 1460
   +---- TCP packet 3: 1460
   +---- ...

The receiver doesn't care.

Your:

recv_all(buffer, 8192)

keeps calling:

recv()

until 8192 bytes have arrived.

Therefore the application sees:

8192 bytes

even though the network may have transmitted them as multiple packets.

That's one of the main reasons recv_all() is necessary.

33. Your library's protocol

You have actually created a very simple protocol.

The receiver follows the exact same protocol:

       ↓

       ↓

       ↓

This is why sender and receiver must agree.

34. One subtle issue: byte order of uint64_t

Your current code does:

send_all(&size, sizeof(size));

and:

recv_all(&size, sizeof(size));

This works when both machines use the same representation, which is common today.

But technically, you're sending the raw machine representation.

For a robust cross-platform protocol, you'd encode the integer into a defined byte order.

For example, your protocol could explicitly define:

file size = 64-bit unsigned integer, network byte order

Your current implementation doesn't do that.

For a project running between your own Linux machines, this is usually not an immediate problem, but it's an important limitation to understand.

35. Another important issue: error handling

You have:

if (inet_pton(...) <= 0)
    return false;

and:

if (connect(...) < 0)
    return false;

That's good as a basic implementation.

But there is a problem:

return false;

doesn't close the socket that was already created.

For example:

fd = socket(...);

if (connect(...) < 0)
    return false;

If connect() fails, fd remains open until the destructor eventually runs.

It's not catastrophic for a short-lived object, but it is cleaner to call:

close_socket();
return false;

in failure paths.

Same issue exists in listen_on() after bind() or listen() fails.

36. Another important C++ issue: copying Socket

This is actually the biggest design issue I'd fix before calling this a robust C++ socket library.

You have:

Socket accept_client() {
    Socket client;
    client.fd = accept(fd, nullptr, nullptr);
    return client;
}

And the class owns a raw file descriptor.

The problem is that raw file descriptors behave differently from ordinary C++ values.

You should eventually make Socket move-only:

Socket(const Socket&) = delete;
Socket& operator=(const Socket&) = delete;

Socket(Socket&& other) noexcept;
Socket& operator=(Socket&& other) noexcept;

Then ownership becomes explicit.

Conceptually:

Socket A
   |
   fd=4
   |
   ↓ move
Socket B
   |
   fd=4

A → fd=-1
B → fd=4

This is especially important as your library gets bigger.

The most important concepts to understand

If you're learning this library rather than just using it, I'd focus on these 8 concepts in this order:

File descriptor — why fd represents the socket.
socket() — creating the kernel socket.
bind() + listen() + accept() — how a server works.
connect() — how a client establishes the connection.
TCP byte stream — why one send() doesn't equal one recv().
send_all() / recv_all() — handling partial transfers.
Your file-transfer protocol — size first, then file bytes.
RAII + move semantics — how to make the C++ wrapper safely own the descriptor.

Once you understand those, you basically understand what this entire header is doing.

One particularly useful next step for your code would be to redesign Socket ownership and then add fork()-based multi-client handling, because that connects directly to the file-transfer program you were working on earlier.
